## Isolated native passphrase migration and second WSL restart

A separate private persistent WSL state root was initialized with the repository's native passphrase provider and a generated test passphrase supplied only over stdin. `profile add` registered an already authenticated, user-authorized Referenced Codex home, checked its existing sign-in, and returned `ready` without copying Codex credentials or starting a new login. This is native readiness detection for existing-sign-in adoption, not evidence of a new browser/device login. The passphrase companion was stopped, restarted, and privately unlocked before migration, so the migration source was a pre-existing non-empty installation rather than a fresh Windows-backed setup. The user's default Windows-backed installation was not altered.

One synthetic supported `state_5.sqlite` history record was created outside the real Identity Home. The user separately authorized metadata-only import from the real Referenced home. The local source review reported 804 supported real sessions; import without consent was rejected, and explicit consent imported those 804 metadata records plus the one synthetic record. No transcript text was imported or reported. Before migration, the isolated state had one Ready profile and 805 retained history records.

With that passphrase owner stopped, plain `codex-folio --state-root` offered migration to Windows-backed WSL protection. Choosing migrate and supplying the generated test passphrase privately completed the transition and reached the ordinary profile picker. The service then reported `running`, `ready`, and vault `unlocked`; the non-secret selection recorded `wsl-dpapi`, and both the protected old-vault recovery material and new Windows-backed vault file existed. The same one profile and 805 history records remained. A launch of that retained real profile forwarded Codex `--version`, returned installed `codex-cli 0.157.1`, and exited 0. The source Identity Home and Codex-owned authentication were not copied or rewritten by this procedure.

After the isolated owner was stopped, the user terminated and restarted the WSL2 distro. The observed new boot began at 2026-09-27 11:35:48 UTC. The persistent private test state survived. Plain startup, with neither a passphrase nor a vault-mode override, reached the retained profile picker and left the detached companion `running`, `ready`, and `unlocked`. One profile remained; history count was 806, one greater than the pre-restart 805, so the observed count shows no loss but does not alone establish row-for-row identity. A second real foreground launch from that retained profile forwarded `--version` and exited 0. The isolated owner was stopped and the user's default companion restored `running`, `ready`, and `unlocked`.

An earlier attempt used `/tmp` for the isolated migration state. WSL removed that test fixture at reboot, making its post-restart result inconclusive. The persistent private state above is the qualification run; no product data-loss result is inferred from the discarded `/tmp` fixture.

The managed-home path is created beneath the app-local state root by the existing profile/home boundary. The ordinary foreground failure was fixed under separately authorized ticket #105 and commit `2a41bdf`; no source fix is included in #102.

After these native checks, the user revoked provider access to the local identities through a browser administration panel. The results above describe the real sign-ins and launches at the time they were observed; they do not assert that the provider access remains valid after revocation. No credential or local Identity Home was modified to re-establish access for this evidence ticket.
