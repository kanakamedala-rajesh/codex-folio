# Decisions

## Settled

1. **Product:** A companion application combining a CLI launcher and local responsive web dashboard. GUI access is optional for identity selection and Codex launch.
2. **Audience:** An open-source GitHub release for individual developers in the MVP. Enterprise integrations are deferred.
3. **Identity model:** Use the term Identity Profile for ChatGPT login identities, workspace contexts, API keys, and later supported credential sources.
4. **Continuity goal:** Preserve repository work across identities. Safe Continuation is guaranteed; Exact Continuation is experimental and must fall back safely.
5. **Authentication:** Codex owns credentials, persistence, refresh, and reauthentication inside each persistent Identity Home. Initial and expired authentication may use browser or device UI.
6. **Dashboard authority:** Read-only. It cannot buy, redeem, reset, update, logout, or otherwise mutate remote account, quota, credit, or workspace information.
7. **Usage scope:** Display the maximum supported Codex usage metadata without prompt, response, command, diff, tool-output, or raw-session content. Label metrics as provider-reported, locally derived, or estimated.
8. **Administrative credentials:** Do not request organization-admin credentials in the MVP. Administrative analytics connectors are future separately permissioned modules.
9. **Application shell:** A native Go executable provides the CLI, local service, and embedded SPA, opened in the system browser. Keep the UI transport-independent for a later native shell.
10. **Tier-one MVP platforms:** Windows AMD64, Linux AMD64, WSL2, and macOS ARM64.
11. **Network boundary:** Bind strictly to loopback in the MVP. Future multi-device support remains possible through a deliberately separated transport and authorization boundary, but no remote mode is implemented now.
12. **Codebase:** Start a new greenfield application and selectively port reviewed components and tests from the prototypes.
13. **Workspace cardinality:** Bind each Identity Profile to one effective Login Identity and Workspace context. Permit multiple profiles for the same Login Identity and treat email as optional display metadata, not identity.
14. **Dashboard actions:** The dashboard may perform relevant non-destructive local operations, but it cannot invoke destructive or remote-mutating operations such as consuming reset credits or updating user or workspace information.
15. **Collection lifecycle:** Collect on demand by default. Offer an explicit service installation for periodic snapshots and native limit alerts; never install autostart silently.
16. **CLI launch:** The companion command opens an interactive Identity Profile selector by default and provides `launch <profile> -- <codex arguments>` for deterministic use. Shell interception is optional and reversible; the installer never replaces the Codex binary automatically.
17. **Experimental compatibility:** Exact Continuation is available only for tested Codex versions. It requires stopped relevant processes, staged backup, App Server validation, automatic rollback, and Safe Continuation fallback.
18. **Working name:** Use VS CodexFolio with CLI command `codex-folio`, subject to formal collision and trademark clearance before release.
19. **Analytics retention:** Store normalized metadata and aggregates in local SQLite for 13 months by default, configurable from 30 days to unlimited. Do not copy raw transcripts; provide safe export and an explicit CLI purge operation.
20. **Profile onboarding:** `codex-folio profile add <alias>` uses browser authentication when available, falls back to device-code authentication, and supports explicit `--browser` and `--device-code` overrides. Ordinary switching reuses Codex-managed persistent authentication.
21. **Local identity management:** The dashboard supports create, read, update, and delete operations on local Identity Profiles with appropriate confirmation and recovery controls. These operations do not modify remote user or workspace information.
22. **State modes:** Ship Isolated Identity Homes as the recommended default and an explicitly experimental Shared Work Home mode for serialized identity switching with shared sessions and configuration.
23. **Default metric scope:** Dashboard metrics default to the currently active Identity Profile. Users may explicitly switch to a combined multi-profile view.
24. **Metric provenance:** Label values as provider-reported, locally derived, estimated, or observed during session. Never present estimated session/quota relationships or observed code changes as exact Codex attribution.
25. **Profile deletion:** After typed alias confirmation, move a deleted local profile and Identity Home to app-local quarantine for seven days by default. Permit CLI restoration, then purge where the platform permits. Deletion does not delete the remote OpenAI identity.
26. **Diagnostics and telemetry:** Keep independently configurable redacted local diagnostics enabled by default. Remote CodexFolio telemetry is disabled by default and requires explicit opt-in.
27. **Shared-home credential vault:** Use encrypted profile records with an OS-protected application key on Windows, macOS, and supported Linux desktops; use a passphrase-encrypted vault for WSL/headless Linux; permit plaintext only as an explicitly acknowledged compatibility fallback. Never colocate the encryption key with ciphertext or silently downgrade.
28. **Safe Continuation artifact:** Guarantee a deterministic repository-first checkpoint that requires no source-profile model quota. Transcript-assisted recovery is separately consented, previewed, editable, and approved; persist and send only the sanitized checkpoint.
29. **Shared configuration:** Use immutable, versioned Shared Configuration Packs projected into Identity Homes with profile-local overrides. Never reverse-sync profile changes automatically; promotion into a shared pack is reviewed and explicit.
30. **Handoff invocation:** Support explicit `codex-folio handoff <target>` and an automatic post-exit offer after an observed quota condition. Rank eligible targets by remaining provider-reported capacity and compatibility; never terminate or replace a running Codex process automatically.
31. **Overview outcome:** The first dashboard viewport answers “Can I continue working, and which identity should I use?” Active-identity limits lead, eligible alternatives follow, and trends and detailed analytics come afterward.
32. **Frontend stack:** Use React, TypeScript, and Vite, embedded as versioned assets in the Go executable. Hide the selected charting dependency behind internal visualization components.
33. **Accessibility and localization:** Require WCAG 2.2 AA, full keyboard access, visible focus, semantic chart alternatives, reduced-motion support, high-contrast resilience, 200% zoom, screen-reader announcements, externalized English copy, and OS-locale formatting.
34. **Visual workflow:** Use comp-first design: approve a high-fidelity visual target before implementing the dashboard.
35. **Information hierarchy:** Make the overview glance-first. Immediate active-profile capacity and eligible alternatives dominate; detailed analytics remain one navigation level deeper.
36. **Narrow-screen behavior:** Preserve overview, profile selection, alerts, and handoff at narrow widths. Convert dense comparisons and tables into accessible drill-down rows without horizontal page scrolling.
37. **Visual direction:** Adopt Signal Rail as the dashboard's comp-first direction. Use its calibrated off-center rail, instrument-like hierarchy, sparse charcoal surfaces, and restrained semantic signal colors; retain explicit text, icons, and patterns so color is never the only carrier of meaning.
38. **Visual fidelity boundary:** Treat the selected comp as the compositional target, not a literal data contract. Correct synthetic ranking inconsistencies, product/model labels, dates, metric provenance, and accessibility issues during implementation.
39. **Safe Continuation storage:** Never generate `.codex-folio` files or other CodexFolio state inside a repository. Leave repository/worktree changes in place and store the sanitized structured checkpoint in encrypted app-local storage keyed by a non-secret repository identity. Launch the target profile in the same working directory; portable checkpoint export is explicit only.
40. **Handoff eligibility:** Apply only companion-observable hard gates before capacity ranking: the target Identity Profile and Identity Home exist, authentication is usable according to Codex's exposed state, and any requested experimental adapter supports the installed Codex version. CodexFolio may display other cautions but does not predict or police Codex model, tool, repository, or workflow compatibility.
41. **Background collection:** The opt-in service uses event-driven collection while Codex is active, lightweight periodic refresh while idle, and exponential backoff after provider or authentication failures. Native notifications are privacy-first and generic by default; detailed identity or quota content requires an explicit per-device opt-in.
42. **Experimental feature gate:** Shared Work Home exact resume and Isolated Identity Home transactional transfer are separate experimental mechanisms. Both require Experimental Features to be enabled plus a version-specific risk acknowledgement; neither is silently enabled by choosing a state mode.
43. **Headless vault lifecycle:** On WSL and headless Linux, the service starts locked after reboot and performs no sensitive collection until the user runs `codex-folio vault unlock` for that user session. Unattended unlock and silent plaintext fallback are excluded from the MVP.
44. **Companion boundary:** CodexFolio complements the user's installed Codex application; it does not reimplement or replace Codex. Its responsibilities are Identity Profile selection, environment/home selection, launching the real Codex executable, read-only metadata collection through supported seams, local analytics, and optional handoff preparation. Codex remains responsible for its UI, authentication behavior, sessions, models, tools, repository operations, configuration semantics, and execution lifecycle.
45. **Supported data sources:** The MVP reads only documented Codex/App Server account and usage interfaces, eligible local Codex metadata without copying transcript content, and CodexFolio's own launch and snapshot records. It does not scrape web UI or call undocumented private endpoints. Missing data is represented explicitly as unsupported, unavailable, stale, or requiring reauthentication.
46. **Snapshot schedule:** On-demand mode collects when the dashboard opens or refreshes, before a CodexFolio launch, after that launched Codex process exits, and through explicit `usage refresh`. The optional service defaults to five-minute refreshes while a CodexFolio-launched process is active, thirty-minute idle refreshes, and refreshes near known reset boundaries, with configurable intervals, a provider-safe floor, and exponential failure backoff.
47. **Combined analytics:** Never combine unrelated quota percentages. Combined mode retains per-profile limits, reports counts such as profiles able to continue, aggregates only comparable absolute local metrics, and keeps API credits or spend separate from subscription limits.
48. **Loopback authorization:** Treat loopback as an authenticated boundary. Use one-time dashboard bootstrap, a short-lived local session, strict Host and Origin validation, no cross-origin access, CSRF protection, and server-side custody of credentials. Sensitive local operations retain stronger confirmation.
49. **Service ownership:** Run at most one CodexFolio service per operating-system user. The CLI discovers and reuses a healthy user-scoped instance or starts one on demand. Persistent service installation is explicit and reversible through `codex-folio service uninstall`.
50. **Normalized metric storage:** Persist only reviewed, allowlisted normalized metric fields. Do not archive raw provider responses. Each observation records its profile, source, provenance, metric type, value/unit where applicable, quota-window boundaries, capture time, freshness, and availability state.
51. **Project Identity:** Recognize repositories through an encrypted app-local canonical-path mapping to a user-editable Project Alias without writing application state into the repository. Send aliases and basenames to the dashboard by default; exclude full paths from browser responses, diagnostics, telemetry, and exports unless explicitly requested.
52. **Activity boundaries:** Distinguish a Managed Launch started by CodexFolio, an Observed Session discovered through supported Codex metadata, and a Usage Snapshot collected at a point in time. Correlate them only when a supported identifier establishes the relationship.
53. **Time semantics:** Store UTC instants together with applicable provider window boundaries and timezone context. Render with the current OS locale/timezone, retain the timezone used for historical calendar buckets, and never reinterpret provider quota windows as artificial calendar weeks.
54. **Purge separation:** `codex-folio analytics purge` removes only scoped analytics, activity metadata, and sanitized checkpoints. Identity Profiles, authentication, configuration packs, and quarantined homes use separate lifecycle operations. Purge supports date/scope filters, a dry-run summary, confirmation, and explicit `--yes` automation.
55. **Profile-state terminology:** Do not use “active identity” as a machine-wide concept in isolated mode. Distinguish the Selected Profile shared by CodexFolio's dashboard and interactive CLI, the Dashboard Scope being viewed, the Launch Profile of each Managed Launch, and the Shared-Home Identity materialized in experimental Shared Work Home mode.
56. **Foreground launch contract:** `codex-folio launch <profile> -- <arguments>` runs the installed Codex executable in the foreground with the selected Identity Home, passes arguments and terminal streams through, forwards signals appropriately, and returns the Codex exit status. Detached Codex execution is outside the MVP.
57. **Reauthentication delegation:** When authentication is required, CodexFolio invokes the installed Codex authentication flow inside the selected Identity Home and launches only after it succeeds. CodexFolio does not implement provider login or inspect credentials; stored browser/device-code preferences may guide the Codex invocation.
58. **Safe Continuation approval:** A sanitized checkpoint must be previewed, optionally edited, and approved before CodexFolio passes it as initial context to a new standard Codex thread. The dashboard supplies an editor; terminal-only use supplies a summary and `$EDITOR`. Cancellation launches nothing, and CodexFolio performs no model call.
59. **Checkpoint retention:** Sanitized repository-first checkpoints expire after 30 days by default; transcript-assisted checkpoints expire after seven days. Both are configurable from one day to unlimited. Successful launch marks a checkpoint completed without immediately deleting it, and analytics purge may remove it sooner.
60. **Shared-home switch transaction:** The experimental Shared Work Home adapter modifies only the authentication representation required for identity selection. It requires an unused Shared Work Home, an exclusive CodexFolio lock, staged backup, atomic target materialization, identity verification through a documented Codex interface, committed vault generation, and automatic restoration on failure. Other shared-home state remains Codex-owned and untouched.
61. **Exact intent:** Safe Continuation is the default for automatic post-exit handoff. Every Exact Continuation attempt requires explicit `--exact` intent or an equally explicit secondary UI action. Failure rolls back and offers the prepared Safe Continuation checkpoint.
62. **Compatibility manifest:** Experimental adapters run only for Codex versions and platforms listed in a compatibility manifest bundled and signed with the CodexFolio release. Remote flags cannot silently enable support for new Codex versions.
63. **Shared-home configuration:** Treat configuration in Shared Work Home as Codex-owned mutable state. Immutable Shared Configuration Packs are optional reviewed baselines beneath shared local overrides; CodexFolio never interprets or reverse-syncs Codex-written changes, and promotion remains explicit.
64. **Continuation guarantee:** Guarantee continuation of local repository work across authenticated Identity Profiles and workspaces by launching a new installed Codex process in the same working directory with an approved repository-first checkpoint. Never promise live identity switching in a running Codex process or exact cross-team thread continuation.
65. **Cross-identity exact attempts:** Exact Continuation may be explicitly attempted across authenticated Identity Profiles, including different workspaces, only after the user attests authorization and no observable managed restriction blocks it. It remains version-gated, transactional, and non-guaranteed; failure rolls back and returns to Safe Continuation.
66. **Dashboard navigation:** Use six primary destinations: Overview, Profiles, Sessions, Analytics, Alerts, and Settings. Handoff remains a contextual action rather than a standalone destination.
67. **Recommendation freshness:** Display exact capture age and withhold the “Recommended” label when provider-reported capacity is older than ten minutes. Stale profiles remain visible below sufficiently fresh candidates and may still be refreshed or launched manually.
68. **MVP alerts:** Support configurable per-profile and per-window warnings at 20% and 10% remaining, quota exhausted, reset approaching, reset-credit expiry approaching, reauthentication required, repeated collection failure, and Shared Work Home recovery required. Do not build a general alert-rule engine in the MVP.
69. **Overview actions:** Limit primary overview actions to Refresh, Launch Codex, Prepare Handoff, and Open details. Destructive, administrative, consent, service, vault, and experimental controls remain in their relevant detail/settings flows with stronger confirmation.
70. **Selected Profile contract:** Persist one Selected Profile shared by the dashboard and interactive CLI. A dashboard profile switch or `codex-folio select <profile>` updates it; bare `codex-folio` highlights it in the selector. Deterministic `launch <profile>` does not mutate it, existing Managed Launches retain their Launch Profile, and Combined Dashboard Scope can never become Selected Profile.
71. **Profiles inventory:** The Profiles route shows alias, optional email/workspace label, authentication type and health, Identity Home mode, assigned Shared Configuration Pack, last successful usage refresh, Selected Profile state, and select/launch/edit/reauthenticate/quarantine actions. Never expose secrets, key values, token fragments, or raw credential locations.
72. **Sessions timeline:** Present Managed Launches and Observed Sessions in one chronological, filterable timeline with explicit record-type and provenance labels. Correlate only through supported identifiers. Details may include timestamps, profile, Project Alias, model/token metadata, exit status, and provenance, but never conversation or tool content.
73. **Analytics tabs:** Use Capacity, Tokens, Projects, Models, Activity, and Compare as tabs within the Analytics destination. Respect Dashboard Scope and the settled non-additive combined-quota rules rather than adding primary navigation destinations.
74. **Export formats:** Provide normalized JSON plus CSV for individual tables and chart-equivalent datasets with profile/project/date/scope filters and a preview of fields and record counts. Use aliases and basenames by default; full paths require explicit inclusion. Exclude credentials, raw source payloads, conversation/tool content, and raw diffs.
75. **Partial-data presentation:** Preserve the layout and last successful evidence when collection fails, showing an explicit stale timestamp, reason, and relevant Refresh, Reauthenticate, or Unsupported action. Show zero only when explicitly reported. Profiles without sufficiently fresh capacity cannot receive recommendation ranking.
76. **Identity Home ownership:** Distinguish Managed Identity Homes created inside CodexFolio's app-local storage from Referenced Identity Homes registered in place. CodexFolio owns the lifecycle of managed homes only; removing a referenced profile never moves, quarantines, or deletes its external home.
77. **Profile naming:** Give every Identity Profile an immutable internal UUID, a unique case-insensitive portable CLI Alias, an independently editable Display Name, and optional email/workspace display metadata. Alias changes do not rename storage or internal references.
78. **Duplicate detection:** Capture only documented account/workspace identifiers and optional metadata after Codex-owned authentication. Warn about an apparent duplicate login/workspace but allow it. The local profile UUID remains authoritative when stable provider identifiers are unavailable.
79. **Ownership-aware removal:** Block removal while a profile has a running Managed Launch, require a replacement before removing Selected Profile, quarantine managed homes for seven days, remove only the registry entry for referenced homes, and remove only the vaulted profile generation for a Shared-Home identity. Always state that the remote OpenAI identity is unaffected.
80. **Prototype migration:** Never automatically import prototype credential blobs or undocumented provider payload caches. A migration assistant may import reviewed non-secret aliases, preferences, Project Aliases, and compatible normalized local aggregates; existing Codex homes may be referenced in place, and unverifiable identities reauthenticate through Codex.
81. **Service integration:** Install the optional collector as an unprivileged native user-session service: per-user Task Scheduler on Windows, LaunchAgent on macOS, `systemd --user` on Linux, and `systemd --user` on WSL2 only when systemd is enabled. Never silently substitute another autostart mechanism.
82. **Application directories:** Use platform-standard user directories and separate configuration, durable data, cache, logs, runtime descriptors, managed homes, and quarantine. WSL uses its Linux-side data and vault. Permit only an explicit absolute app-data-root override for portable or test scenarios.
83. **Archive-first distribution:** Ship one native executable archive per tier-one OS/architecture with `install.sh` or `install.ps1`, deferring MSI, PKG, DEB, RPM, Homebrew, and WinGet packaging. Each archive contains the CLI, service, and embedded dashboard; native service installation remains available through the CLI.
84. **MVP updates:** Provide opt-in update notification with version, release notes, verified download location, and installer instructions. Do not self-replace the running executable or automatically update Codex in the MVP.
85. **Capability-level compatibility:** Keep basic profile selection and transparent foreground launching available wherever the installed Codex executable works. Report documented metadata integrations and experimental adapters independently as supported, degraded, or disabled for the installed Codex version.
86. **SQLite protection:** Use ordinary pure-Go SQLite under restrictive user-only filesystem permissions and encrypt sensitive fields/blobs through the tiered vault. Encrypt canonical project paths, sanitized checkpoints, and sensitive migration/recovery metadata; keep normalized non-secret usage facts queryable. Credentials never enter SQLite.
87. **Offline frontend:** Bundle every production SPA asset, dependency, and font into versioned assets embedded by Go. Use no CDN or runtime package download, fail builds on lockfile/generated-asset drift, and enforce a restrictive CSP. Only explicitly enabled update and telemetry requests may reach CodexFolio-operated endpoints.
88. **Stable signing gate:** Stable artifacts require checksums, Sigstore/keyless signatures, GitHub artifact attestations, SBOM, provenance, Windows Authenticode signing, and macOS Developer ID signing/notarization. Clearly separate unsigned development/prerelease artifacts from stable installation guidance.
89. **Local diagnostics:** Enable redacted structured diagnostics by default with fourteen-day retention, a 50 MB cap, and age/size rotation. Store only operational component and stable error information; exclude identity/workspace/project labels, paths, usage values, session content, credentials, and command arguments. Level, retention, and disablement are independently configurable.
90. **Remote telemetry transport:** Opt-in telemetry uses no third-party analytics SDK and sends only allowlisted CodexFolio product events to a project-controlled HTTPS endpoint. The public versioned schema may contain app version, OS family/architecture, coarse feature, outcome, stable error code, duration bucket, and resettable random installation ID. If the endpoint and retention policy are unavailable, omit remote collection rather than substitute a service.
91. **Production architecture:** Build a modular monolith with feature-owned deep modules and hexagonal seams only where behavior truly varies: installed Codex, operating-system facilities, persistence/vault, browser transport, update/telemetry endpoints, and test adapters. Keep one Go module, one frontend workspace, one executable, and one user-scoped state owner; enforce inward dependency direction without creating interface-per-type ceremony.
92. **Generated browser contract:** Publish a versioned OpenAPI contract from the loopback service and generate the TypeScript transport client. The SPA never calls Codex App Server, local files, SQLite, or the vault directly. Stable machine-readable domain error codes are mapped to externalized UI copy.
93. **State and launch ownership:** The service is the sole writable owner of SQLite and vault state. For foreground launch, it returns a validated Launch Plan and lease to the CLI; the CLI starts the installed Codex child with direct terminal/signal passthrough and reports lifecycle events. This keeps state serialized without proxying the terminal through the service.
94. **Layered verification:** Require Go unit/race tests, SQLite migration/rollback tests, sanitized adapter contracts, fake-Codex launch/auth/signal/exit tests, browser component/accessibility/E2E tests, native OS/WSL smoke tests, and archive/service install/uninstall tests. CI never uses real identities or production credentials.
95. **Experimental release gate:** Qualify each experimental adapter version with isolated transaction fixtures and manual release testing on disposable identities. Cover interrupted writes, stale locks, wrong identity, unsupported schema, rollback, crash recovery, and Safe Continuation fallback; remove compatibility whenever an invariant fails.
96. **Telemetry consent and retention:** Version remote-telemetry consent against the public schema, permit immediate revocation and installation-ID reset, retain individual allowlisted events for 30 days, and retain anonymous product-health aggregates for 13 months without reconstructing identities.
97. **Diagnostic bundle:** `codex-folio diagnostics export` creates a local, previewed support bundle containing application/schema versions, platform family/architecture, enabled feature states, stable component/error codes, redacted local diagnostics, and service/database health. It never automatically uploads, opens an issue, or includes profile/project/usage/Codex content.
98. **Portable configuration:** Provide a versioned explicit bundle for non-secret settings, Shared Configuration Packs, alert rules, display preferences, and optional Project Aliases. Exclude authentication, vault keys, Identity Homes, full paths, telemetry identifiers, and usage/session history by default. This is preparation for future multi-device migration, not synchronization.
99. **Credential portability:** Do not implement portable credential backup or cross-device vault migration in the MVP. Import non-secret profile definitions on a new device and invoke Codex-owned reauthentication; do not promise or bypass native OS credential-backup behavior.
100. **SQLite recovery:** Maintain three rotating app-local, encryption-aware database backups before migrations and at successful recovery checkpoints. On corruption or migration failure, stop writes, preserve the damaged database, and offer verification, explicit rollback, or redacted export. Never silently recreate an empty database.
101. **First-run setup:** Provide a resumable staged terminal/dashboard workflow that validates installed Codex, defaults to Isolated Identity Homes, offers existing-home registration, authenticates profiles through Codex, selects the initial profile, optionally assigns configuration, and separately offers service/telemetry choices. Configure Shared Work Home and Exact Continuation later under Experimental Features.
102. **Codex discovery:** Search `PATH`, validate candidates with a non-mutating version command, display the resolved path/version, and permit an explicit absolute `--codex-bin` override. Never download, update, or claim ownership of Codex; reject aliases, unresolved relative paths, and invalid candidates.
103. **Automated setup:** Support non-interactive setup only when every required and consent-bearing choice is supplied explicitly. Service, telemetry, Shared Work Home, plaintext fallback, and experimental features never inherit implicit approval; missing choices fail closed with precise guidance.
104. **Shell integration:** Generate versioned completion/optional wrapper integration in app-local storage and print a source line the user may add. Never edit shell startup files or replace the Codex binary automatically. Removal deletes generated integration and identifies the source line for the user to remove.
105. **Setup recovery:** Commit completed setup stages independently, verify them on resume, and continue from incomplete work. Keep profiles Pending and unselectable until Codex authentication and Identity Home validation succeed.
106. **Theme behavior:** Support complete dark and light Signal Rail themes and default to the operating-system preference. Preserve hierarchy, semantic redundancy, contrast, and provenance in both themes and support forced/high-contrast modes independently.
107. **Responsive navigation:** Use a persistent labeled rail on wide screens, an accessible compact icon rail at medium widths, and a narrow-screen top profile/status bar plus bottom navigation for Overview, Profiles, and Alerts with Sessions, Analytics, and Settings under More. Keep Handoff contextual.
108. **MVP density:** Ship one carefully tuned responsive density. Prioritize 200% zoom, keyboard/touch targets, and readable telemetry; defer user-selectable compact/comfortable modes.
109. **Chart selection:** Keep visualization contracts library-independent and choose the concrete charting layer through a frontend-foundation benchmark covering bundle size, keyboard/screen-reader behavior, table synchronization, resizing, reduced motion, high contrast, and 13-month performance.
110. **Comp acceptance set:** Do not begin production UI implementation until Signal Rail acceptance targets cover wide/narrow Overview, Profiles/onboarding, Sessions/detail, Analytics capacity/compare with tables, Alerts/Settings, Safe Continuation/handoff, and empty/stale/reauthentication/offline/recovery states. The selected overview comp remains compositional option one.
111. **UI/UX skill gate:** Frontend implementation must explicitly use the applicable available UI/UX skills. Continue visual shaping and review with `impeccable`; use `image-to-code` for comp-faithful implementation, `build-web-apps:frontend-app-builder` for the new dashboard foundation, `build-web-apps:react-best-practices` for React performance, and `build-web-apps:frontend-testing-debugging` for browser acceptance and regression work. Record skill-driven decisions and verification evidence in the implementation milestones.
112. **CLI command tree:** Use a noun-oriented command surface covering setup/dashboard/select/launch/handoff; profile, usage, analytics, service, vault, configuration-pack, diagnostics, update, and version operations; and a separate experimental namespace for rare Shared Work Home recovery. Bare `codex-folio` remains the interactive selector-and-launch path.
113. **Automation contract:** Applicable commands support `--json`, stable documented exit codes, stdout data, and stderr diagnostics. `--non-interactive` forbids prompts. `--yes` cannot grant telemetry consent, enable experiments, accept plaintext credential fallback, or attest cross-workspace authorization.
114. **Experimental visibility:** Identify experimental behavior through explicit settings/acknowledgement, CLI flags or namespace, dashboard badges/confirmation, and separate compatibility health. Configuration import alone cannot enable it.
115. **Open-source governance:** License under Apache-2.0, use Developer Certificate of Origin sign-off instead of a CLA, publish security/contribution/conduct/support/roadmap guidance, and grant no trademark rights to the working product name or branding.
116. **Telemetry release dependency:** Ship the telemetry client behind its opt-in interface, but expose enablement only when the project-controlled endpoint, public schema, privacy notice, retention jobs, and deletion/reset behavior are operational. Telemetry is never a release blocker for core local features.
117. **Portable checkpoint export:** Export approved sanitized checkpoints as a versioned encrypted `.cfolio` artifact by default, excluding credentials, raw transcripts/diffs, Identity Homes, and repository files. Plain JSON requires explicit `--plaintext` acknowledgement and preview and remains distinct from analytics and configuration exports.
118. **Experimental release independence:** Stable MVP completion depends on the isolated-profile launcher, dashboard, Safe Continuation, service/alerts, and production hardening. Shared Work Home and Exact Continuation ship disabled by default only for qualified compatibility-manifest entries; a failed experimental qualification does not block the dependable core.
119. **Delivery order:** Implement through gated vertical milestones: foundation; profiles/launch/auth; collection/dashboard/analytics; Safe Continuation/export/lifecycle/recovery; service/alerts/diagnostics/portable configuration; experimental adapters; and cross-platform accessibility/security/signing/release hardening.
120. **Regression budgets:** Target under 300 ms warm launch overhead, cached dashboard content within one second, provider refresh normally within ten seconds excluding authentication, under 75 MB idle service memory, under 1% average idle CPU, bounded SQLite writes, responsive 13-month history, and archive review above 50 MB. Treat these as engineering budgets, not marketing guarantees.
121. **Rolling Codex qualification:** Test documented integrations against current stable Codex and the two preceding obtainable supported versions for each CodexFolio release. Permit transparent basic launch outside the tested window with a warning, degrade metadata per capability, and restrict experiments to exact manifest entries.
122. **Stable release gate:** Require threat/security review; credential/log/browser tests; migration/backup/corruption/rollback tests; native tier-one smoke tests; WCAG 2.2 AA audit; keyboard/screen-reader flows; Signal Rail visual/responsive comparison; install/service/update/uninstall verification; SBOM/provenance/signatures/platform signing; complete recovery/privacy/limitations documentation; and an RC soak without unresolved critical defects.

## Authentication friction clarification

An Identity Profile's persistent Identity Home retains the authentication that Codex created and refreshes. Selecting another profile launches Codex with that other persistent home; it does not run `codex login` on every switch. Interactive authentication occurs only during first-time onboarding or when Codex reports that the stored session must be renewed.

## Requested dashboard scope

- Aggregated and per-profile Codex usage overview.
- Primary, five-hour, weekly, and additional usage windows when provider-reported.
- Reset-credit availability and expiry in the user's local timezone.
- Local input, output, cached-input, and other available token categories.
- Interactive usage and trend visualizations.
- Model and project usage breakdowns.
- Health and diagnostics.
- Online profile summary and recent provider-reported usage.
- Session metadata including local date/time, token usage, model, project, and available or estimated quota relationship.
- Identity switching and CRUD for local Identity Profiles.
- Filters, comparison views, safe exports, and useful non-destructive local actions.
- Code-change metrics where attribution can be derived honestly; unsupported attribution must not be presented as exact.

## Implementation elaboration after shared-understanding confirmation

The design-decision frontier is empty. The following are engineering specifications, fact-finding, and production artifacts to create during planning and implementation rather than unresolved user preferences:

- Concrete crash-recovery journal and platform filesystem operations for the settled Shared Work Home authentication-only transaction.
- Exact Safe Continuation redaction patterns and `.cfolio` cryptographic/container specification; review, expiry, and encrypted-default export behavior are settled.
- Detailed authorization-warning copy and the contents/testing workflow for the bundled Exact Continuation compatibility manifest; the guarantee boundary is settled.
- Detailed SQLite tables, indexes, migrations, and aggregation queries within the settled normalized schema and combined-view rules.
- Provider-safe refresh-floor discovery and exact native service manifests/removal tests; the user-session mechanisms are settled.
- Exact frontend asset build/reproducibility workflow and archive release tooling.
- Production acceptance comps and detailed component copy/specifications for the settled Signal Rail route/state set; themes, navigation, and density are settled.
- Signing/notarization credentials, CI runner matrix, and later native-package roadmap; archive-first packaging, MVP update behavior, and compatibility policy are settled.
- Exact field mapping and validation tests for the settled non-secret prototype migration assistant.
- Project-controlled telemetry backend deployment/deletion operations; consent evidence and 30-day event/13-month anonymous-aggregate retention are settled.
